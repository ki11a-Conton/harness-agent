# TASK: VS-001 (TaskVerifier + filesystem tool set)

## Goal

Implement the verification service `TaskVerifier` in `packages/tools` (implements the `Verifier` interface from `@ar/contracts`), plus the filesystem tool set (read/write/edit/search) and `exec` that the verification pipeline and early runtime depend on.

## Status

已完成 — implementation and tests delivered; execution evidence is recorded by the main session (see Verification section below).

## Why

A task is complete only when objective, machine-checkable evidence says so. `TaskVerifier` executes `TaskSpec.verification` specs so completion is decided by executable truth (exit codes, artifact existence, changed files) rather than by the agent's own claim. Fail-closed semantics guarantee no fake passes while the model reviewer is absent.

## Dependencies

CONTRACT-001 (`VerificationSpec` / `VerificationContext` / `VerificationResult` / `Verifier` in `packages/contracts/src/verification.ts`), SEC-001 (`matchGlob` for `search_files`), TOOL-001 (ToolRegistry / ToolOrchestrator pipeline that hosts the tools).

## Contract Notes

- Spec kinds executed: `command`, `artifact`, `requirement` (`review` exists in the contract but is not implemented).
- Check evidence: `command` → `{ type: "test", "exit code N in Xms" }`; `artifact` → `{ type: "file", found/missing }`.
- Failures surface as check-level `error` with code `VERIFICATION_FAILED` (`retryable: false`, `safeToRetry: false` per contract defaults).
- Verifier command checks use ProcessExecutor with fixed `timeoutMs=120_000`, `maxOutputBytes=1_048_576`, `cwd=context.cwd`.
- `passed` is `checks.length > 0 && every check passed`; empty spec list ⇒ `passed: false`.

## Key Design Decisions

1. **Three verification states.** `command` → pass iff exit code 0 (via ProcessExecutor); `artifact` → pass iff the path exists (realpathSync, fallback existsSync) and, when `mustChange: true`, the path appears in `context.changedPaths`; `requirement` → **fails closed**: returns `VERIFICATION_FAILED` unconditionally until a model reviewer is wired — explicit refusal of fake passes, per the documented limitation.
2. **Path normalization for `changedPathsContain`.** Relative paths in `changedPaths` are resolved against `context.cwd`; artifact `spec.path` is resolved the same way when relative. Comparison is case-insensitive with separators normalized to `/` (`normalize(): split(sep).join("/").toLowerCase()`), so Windows drive/case variance cannot cause false negatives. Must-change checks use the resolved absolute path, so relative vs absolute representations of the same file match.
3. **Level semantics.** `checks.length === 0` ⇒ `level 0` (no specs defined); all checks passed ⇒ `level 3`; any check failed ⇒ `level 1`. Levels 2/4/5 are reserved by the contract (partial/review tiers) and not produced.
4. **Pure service, no policy short-circuits.** The verifier runs no permission/sandbox/approval logic: commands are assumed pre-authorized by the agent runtime, and artifacts are checked against the run's `changedPaths` as recorded by tools. Enforcement stays solely in ToolOrchestrator (TOOL-001/002, SEC-001).
5. **Filesystem tool path contracts (delivered with VS-001).** `write_file` / `edit_file` / `search_files` resolve relative input paths against `context.cwd` (`resolve(cwd, path)`); failure maps to `PROCESS_ERROR`. `edit_file` refuses to guess: a missing anchor returns `failed` with `PROCESS_ERROR` ("anchor not found"), never a silent no-op. `search_files` caps results (schema max 10_000, default 1000) and returns workspace-relative POSIX paths. All policy (sandbox path checks, permissions) stays in the orchestrator; the tools are policy-neutral.

## Test Coverage

### TaskVerifier unit tests (`task-verifier.test.ts`, 8 cases)

1. command exit 0 → `passed: true`, level 3, evidence `type: "test"`
2. command exit 1 → `passed: false`, `VERIFICATION_FAILED`, level 1
3. artifact exists → pass, evidence `type: "file"`
4. artifact missing → fail with error
5. `mustChange: true` passes with path in `changedPaths`, fails with empty `changedPaths` (relative + absolute forms)
6. requirement → fail-closed `VERIFICATION_FAILED` with no reviewer
7. empty spec list → `passed: false`, level 0
8. mixed command+artifact with one failure → whole run fails, both checks reported

### Integration tests (`vs001.test.ts`, 11 cases)

Filesystem set through orchestrator (6):
1. `write_file` → `read_file` roundtrip (relative vs absolute path), file evidence
2. `write_file` append mode produces concatenated content
3. `write_file` outside workspace → `denied` / `SANDBOX_DENIED` (sandbox enforcement)
4. `edit_file` first-occurrence replace; missing anchor → `failed` / `PROCESS_ERROR`("anchor not found")
5. `edit_file` `replaceAll` → 3 replacements
6. `search_files` glob `**/*.ts` and basename match, workspace-relative results

Exec through orchestrator (5):
7. allowlisted command runs, stdout captured
8. command not in allowlist → `denied` / `SANDBOX_DENIED`
9. `tool.output` events streamed with text payload
10. long-running command → `timeout` / `PROCESS_TIMEOUT`
11. elevated exec with `defaultEffect: "ask"` routes through approval store; allow resolves to success

## Acceptance Criteria

- `TaskVerifier` implements the `Verifier` contract and executes all three spec kinds.
- Command checks pass/fail on exit code with evidence.
- Artifact checks verify existence and optional must-change against normalized changedPaths.
- Requirement checks fail closed; no code path fabricates a pass.
- Level semantics hold: 0 (no specs) / 3 (all pass) / 1 (any failure).
- Verifier contains no permission/sandbox/approval logic.
- Filesystem tools enforce path safety (resolve against `context.cwd`), anchor-missing → `PROCESS_ERROR`, `maxResults` caps; integration tests prove sandbox denials and approval routing still work end-to-end.
- `pnpm typecheck` and `pnpm test` green.

## Known Limitations / Residual Risk

- **`requirement` kind is unimplemented by design**: a model reviewer (`VerificationCheckKind "review"`, levels 2/4/5) is not wired yet; such specs always fail closed. Intentional, to be replaced once a reviewer lands.
- `read_file` resolves the platform path verbatim (no `resolve(cwd, path)`); callers must pass absolute paths (as the integration test does).
- Verifier command checks assume the process sandbox is already configured by the runtime; they do not apply an allowlist themselves.
- Fixing level tiers and the `review` check kind are future work (VSI later tasks).
