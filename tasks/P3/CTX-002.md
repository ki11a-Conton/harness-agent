# TASK: CTX-002

## Status

In Progress（主会话待验收）

## Goal

Implement `BudgetPlannerImpl` in `packages/context` (`@ar/context`): deterministic context budget planning — a hard token ceiling, priority eviction, and security-policy protection — per AGENT_ARCHITECTURE_PLAN v2.0 §36, §112, §184 (build order `13 context`).

## Why

The context builder must pack blocks under a hard ceiling while reporting `used` / `available` / `dropped` / `compressed` (§36), and it must never evict security-policy content (§112 "no security policy eviction"). Evicting `system`/`user` or `trusted` blocks would silently remove the invariants (permission rules, sandbox policy, user constraints) the loop is bound to honor — the ceiling must yield to protected content, and the overflow must be reported truthfully for compaction (CTX-003) to resolve.

## Dependencies

- CONTRACT-001 — `ContextBudget` / `ContextReport` in `packages/contracts/src/limits.ts`; `BudgetPlan` / `BudgetPlanner` / `ContextBlock` in the P3 extension section of `packages/contracts/src/context.ts`. No dependency on CTX-001 / CTX-003 (pure contract-level, parallelizable).

## Scope

### Create

- `packages/context/src/budget.ts` — `BudgetPlannerImpl implements BudgetPlanner`; pure, synchronous, deterministic:
  - `plan(blocks, budget)` → `BudgetPlan`
  - spendable headroom = `maxTokens - (reserved.system + reserved.task + reserved.output)`; reserved amounts are held back and never consumed by the planner
  - never-evict blocks (source in `NEVER_COMPACT_SOURCES` — `system`/`user` — or `trust: "trusted"`) are always selected first, in input order, under any budget pressure
  - ordinary blocks are stable-sorted by `priority` descending (ties keep input order) and admitted while the running total fits the headroom; the rest go to `dropped`
  - report: `used` = sum of selected block tokens; `available` = `maxTokens - used` (may be negative when never-evict blocks alone exceed the ceiling); `dropped` = number dropped; `compressed` = 0 (this planner never compresses)
  - empty input → all-zero report
  - `budget.dynamic` is accepted but ignored (documented in code)

### Forbidden

- No eviction of never-evict blocks under any budget pressure
- No randomness or input-order dependence in admission decisions (deterministic for a given input)
- No cross-package imports beyond `@ar/contracts`

## Key Design Decisions

- **hard ceiling with a protected tier** — `maxTokens` is a hard ceiling for ordinary blocks; the never-evict tier (system/user per `NEVER_COMPACT_SOURCES`, or `trust: "trusted"`) always fits because the ceiling yields to it — the direct mechanism for "no security policy eviction" (§112).
- **priority descending, stable** — eviction order is fully determined by `priority` (descending); equal priorities keep input order, so planning is deterministic.
- **never-evict overflow is reported, not resolved** — if protected blocks alone exceed `maxTokens`, all are kept, `report.used` truthfully exceeds the ceiling and `available` goes negative; resolving the overflow is CTX-003 / the caller's job (compaction, not eviction, is the sanctioned response for protected content). This planner reports the facts.
- **token accounting is the caller's** — `ContextBlock.tokens` is provided by the caller (`chars/4` heuristic upstream); the planner performs no estimation, it only sums the field, keeping planning a pure arithmetic function over contract fields.
- **`dynamic` is reserved** — the contract field exists but is ignored in this phase; headroom derives from `reserved` only (marked in code as reserved for later).
- **metrics are always emitted** — every call returns a full `ContextReport` (zeroed for empty input), satisfying §112 "metrics emitted".

## Tests

- Hard ceiling: ordinary blocks can never push `selected` over the spendable headroom; overflow blocks land in `dropped`
- Priority eviction: lower-priority blocks are evicted before higher-priority ones
- Trusted protection: `trust: "trusted"` and `system`/`user` blocks are never dropped, even at full budget
- Never-evict overflow semantics: never-evict blocks alone > `maxTokens` → all kept, `used` > ceiling, `available` negative, zero ordinary blocks admitted
- Report consistency: `used` equals the sum of selected tokens; `available` = `maxTokens - used`; `dropped` = `dropped.length`
- Determinism: same input twice → identical plan; priority ordering independent of insertion sequence
- Reserved area: `reserved.system/task/output` are held back — ordinary blocks consume only the headroom, never the reserved amounts

## Acceptance Criteria

From plan §112 (verbatim): "Context budget."; Acceptance: `hard token ceiling`, `priority eviction`, `no security policy eviction`, `metrics emitted`.

From plan §36 (verbatim): "The context builder must report: `used`, `available`, `dropped`, `compressed`" — the planner emits all four in `ContextReport` on every call.

## Residual Risks

- **Token estimation is out of scope here** — `ContextBlock.tokens` is trusted as given by the caller (chars/4 heuristic); a bad estimate yields a mis-sized plan, but the planner has no estimation responsibility (the field lives on the block by contract, and the planner does not re-estimate).
- **Never-evict overflow is handed upward** — when protected content exceeds the ceiling, this planner only reports negative `available`; the loop must invoke CTX-003 (compaction) or otherwise resolve overflow before planning again, or the over-budget context is emitted as-is.
- **`dynamic` is inert** — no dynamic headroom semantics are implemented in this phase; the field's presence in the contract is forward-compatible but currently ignored.
