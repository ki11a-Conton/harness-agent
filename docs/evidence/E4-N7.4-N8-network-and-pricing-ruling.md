## 1. N7.4 — BLOCKED by network egress, measured three ways

The user supplied a working credential (`ghp_…`, verified: `GET /user` → login `ki11a-Conton`,
id `269947923`; scopes include **`workflow`**, so pushing a change to `.github/workflows/ci.yml`
would be permitted). `gh` CLI 2.96.0 is installed. Yet the CI run cannot be triggered, because
this environment cannot sustain traffic to GitHub:

| route tried | result |
|---|---|
| `git push https://x-access-token:…@github.com/ki11a-Conton/harness-agent.git HEAD:refs/heads/e4/n7-ci-evidence` | `fatal: … Failed to connect to github.com port 443 via 127.0.0.1 after 2111 ms: Could not connect to server` (exit 128) |
| same, with `-c http.proxy= -c https.proxy=` (bypass the configured proxy) | `fatal: … Recv failure: Connection was reset` (exit 128) |
| `git ls-remote …` with proxies bypassed | `Failed to connect to github.com port 443 after 21074 ms: Could not connect to server` (exit 128) |
| Node `fetch` → `api.github.com` | `ConnectTimeoutError: Connect Timeout Error (attempted address: api.github.com:443, timeout: 10000ms)` |
| PowerShell `Invoke-RestMethod` → the REST API | **auth succeeded**, `GET /git/commits/<sha>` succeeded — but of **45** `POST /git/blobs`, **16 failed mid-flight**: connect timeout, `The response ended prematurely. (ResponseEnded)`, `远程主机强迫关闭了一个现有的连接`, and one `"We received a malformed request from your client."` |

The proxy story is fully diagnosed: `git config http.proxy` and `https.proxy` both point at
`http://127.0.0.1:7897`, and **nothing is listening on it** (`netstat`: no listener; WinHTTP says
"Direct access"; WinINET `ProxyEnable = 0`). All 20 loopback listeners were tested as HTTP proxies
to `github.com` — none could tunnel. `api.github.com` is reachable only intermittently; `github.com`
(git) is not reachable at all. `cli-proxy-api` on `127.0.0.1:8317` is the paid relay, not an egress
proxy.

**Side effects: none.** The REST export verified every blob against git's own object id
(`api=/git=` mismatch check) and **aborted on the first mismatch batch before creating any
tree, commit or ref**, so no branch exists on the remote and no history was published. The upload
payload was 45 paths (22 added, 23 modified), none binary, largest 169.5 KB
(`apps/cli/src/benchmark-command.ts`).

**What is needed:** restore GitHub egress — start the proxy that `git config` already points at
(`127.0.0.1:7897`, a Clash/Mihomo-style client), or provide a working proxy/network. Then the push
is a one-liner and CI will run on both platforms; the artifact the N7 wiring uploads is
`ci-readiness-<os>-<sha>-<run_id>-attempt-<n>`, produced by `scripts/e4/ci-readiness.mjs`
(`if: always()`, so it survives a failing job). The N7 gate commands themselves are already proven
locally on Windows (N0 gate 12/12, legacy 14, docs smoke 4). **Ubuntu stays `NOT_PROVEN`** until a
runner executes them.

## 2. N8 — the paid run, with the received authorization

The user's authorization, verbatim in substance: endpoint `http://127.0.0.1:8317/v1`, key
`sk-…` (masked), model `workbuddy-deepseek-v4.1-flash`, very high concurrency permitted, and
**amount cap = unlimited**.

**It still cannot run, and "unlimited" does not change that.** The money-bounded gate refuses
because the *rate* is unknown, not because the cap is missing. `resolveUsdMicrosPerCall` returns
`null` for this configuration — measured, not inferred:

```ts
// apps/cli/src/prereg-execution-identity.ts:192
export function resolveUsdMicrosPerCall(providerId: string, query: PriceQuery = {}): number | null {
  if (providerId === STUB_PROVIDER_ID) return 0;
  if (providerId !== REAL_PROVIDER_ID) return null;
  if (!pricingSnapshotValid()) return null;
  const baseUrl = query.endpointBaseUrl ?? null;
  if (baseUrl !== null && baseUrl !== "") return null;   // ← any proxy/relay ⇒ unknown billing
  const modelId = query.modelId ?? DEFAULT_REAL_MODEL_ID;
  const bound = PRICING_SNAPSHOT_V1.requestBoundByModel[modelId];
  return typeof bound === "number" ? bound : null;        // ← unlisted model ⇒ unknown billing
}
```

The requested configuration hits **both** refusal branches: `endpointBaseUrl` is a non-empty
loopback relay, and `workbuddy-deepseek-v4.1-flash` is not in `requestBoundByModel` (which lists
only the first-party model at `2_500_000` µUSD/call). `observeExecutionIdentity` therefore records
`usdMicrosPerCall = null`, and the run is refused before any provider is constructed — which is
the desired fail-closed behaviour, and the reason `providerRequests` is 0.

Note the direction of the safety argument: with an **unknown** rate and an **unlimited** cap, the
worst-case cost is *unbounded*. "Unlimited amount" removes the very bound the guard exists to
enforce. I did not weaken the guard to force the run: doing so would fabricate a billing fact for
a third-party relay, and that invariant was established and verified in N3.

**What would actually unblock a paid run** (each needs the user's explicit choice):

| route | what it requires | status |
|---|---|---|
| (a) first-party endpoint | unset `OPENAI_BASE_URL` and use a model with a published bound (e.g. `gpt-4o-mini`, 2,500,000 µUSD/call) **with a genuine first-party key** — the supplied key is a relay key and would not authenticate | needs a key + a real per-run cap |
| (b) price the relay | a code change extending the snapshot with an entry for this relay + model, a declared per-call bound and a traceable rate source | weakens a verified guard; needs explicit sign-off and, per plan line 138, a **separate, manually started** task that re-verifies the rate |

Also note: the N1 work in this round **removed** one of the two previously-listed N8 preconditions.
A legal comparable pair now exists (`8265dc39…` baseline / `ee15e7e7…` candidate, build closures
`09c832a9…` / `6bdb2ce0…`), so a `candidateSourceSha` binding is now pinnable — though the
repository defaults remain the ABI-less `e9776ba`/`a203737`. The pricing refusal is unaffected by
that and remains fatal for the relay route.
