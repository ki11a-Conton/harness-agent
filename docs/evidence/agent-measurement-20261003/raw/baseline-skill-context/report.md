## Two concrete limitations

The existing selector tokenizes ASCII alphanumerics only:

- `typescript compiler fix diagnostic errors` selects the intended one skill.
- `修复类型检查错误` produces an empty token set and selects all 100 skills.
- `修复 TypeScript 类型检查错误` selects no skills because its single recognized token scores below the default threshold.
- `compile-check` selects the named skill in this fixture, but explicit skill-name preservation is not an independent invariant; a sufficiently long description can lower Jaccard below the cutoff.

The skill ledger also attributes injections/outcomes before actual budget admission. In the 16k run, actual requests contain only 17 bodies each (34 admissions total), while every one of the 100 skills records injectedCount 2 (200 total) and completedCount 1. Unadmitted bodies therefore receive injection-token cost and successful-task feedback. This is a deterministic Harness attribution defect; it cannot be used as evidence that all selected skills helped the task. The duplicate facts are retained in `baseline-tight.json`.

`model.started.contextBlockIds` lists only existing prior blocks in this baseline, not skill bodies generated by the pipeline. First request IDs are empty although 17 bodies are actually present. That field alone cannot prove skill admission. Use actual request bytes or existing `context.selected` events correlated to a successful build/model call, retaining complete step identity and avoiding asynchronous telemetry races.

## Proposed next single strategy change

Implement an opt-in, versioned **task-scoped skill selection** challenger in the agent/host layer using the existing selection and body-loading interfaces. Its one semantic difference is the selected metadata-name set. Keep all existing security scanning, capability gates, revision snapshots, tool schemas, prompt, budgets and verification unchanged. Default stays identity.

The challenger must preserve explicitly named skills and trusted host-configured required skill names. An unknown task/no confident relevance signal must fall back to the full index, not silently remove all knowledge. Avoid using untrusted tool-output strings as selection authority. An English-only fixed-task measurement here does not authorize assuming Chinese-to-English relevance; multilingual rules and unknown-task fallback need explicit negative fixtures. Tie the fixed task goal to the actual TaskSpec/run identity; if it differs from the active task, retain the full index. Do not widen the frozen Core API merely to guess task relevance.

Acceptance:

1. Baseline and challenger run byte-identical task fixtures under fixed independent TaskVerifier; original task/user-message, tool/permission/sandbox/verification digests remain equal.
2. Freeze skill files, source and selection config hashes. Record selected/admitted names, body hashes, full request bytes, actual filesystem operations and tool traces for AB/BA repeats.
3. This 100-skill fixture must keep the target in all requests and reduce serialized system bytes by at least 90%; original read tool result must be identical.
4. A separate late-sorting relevant-skill, tight-budget case must retain the skill body and pass the same independent content checker. This probe does not manufacture model-success evidence from its first-sorting target.
5. Explicit/required skills survive lexical cutoff and k; unrelated/empty/unknown-language tasks keep the index; invalid/denied skill bodies remain excluded; concurrent tasks cannot share a fixed-goal closure inadvertently.
6. Actual step skill snapshots witness only admitted bodies, existing context boundaries pass, relevant unit/integration/security/typecheck checks pass. Live paired model performance is separately measured before any promotion.

Separately fix the proven Harness admission-feedback defect with red/green budget-drop and denied-load tests. A strategy should not be rewarded using the current inflated ledger. That correctness repair and selection challenger are distinct changes and should retain distinct evidence.
