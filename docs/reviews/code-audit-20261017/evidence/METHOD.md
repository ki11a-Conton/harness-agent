# 全仓库代码审查 · 统一方法与产出规范

本文件是 Lead 与所有审查员的共同约定。**先完整读完本文件再开始**。

## 0. 任务边界（硬约束）

- 目标：**只记录，不修改任何代码**。禁止 `edit` / `write` 任何被 git 跟踪的文件；禁止 `git checkout` / `git reset` / `git stash` / `git commit`；禁止 `pnpm install` 改动 lockfile。
- 允许写：**你自己的 part 文件**（路径见任务描述）以及 `.ci/tmp/review/` 下你自己的临时脚本。
- 禁止越界写别人的 part 文件。
- 只读分析可以用任意命令，但**不要重启 8787 服务**、不要动用户桌面 DSH 安装（`D:\666desktop`、`C:\Users\MECHREV\.dsh`）。
- 仓库根：`D:\Download games\harness agent`。PowerShell 必须是 7.6.5（`pwsh`）。
- 该仓库没有 ESLint / knip / prettier 配置，唯一的静态检查是 TypeScript（`pnpm typecheck` = `tsc -b`）。**没有现成 linter 可依赖，风险与死代码结论必须自己用证据支撑。**

## 1. 分类（每条发现必须归入其一）

| 代号 | 含义 |
| --- | --- |
| `A` | 可优化点：重复逻辑、过长函数/文件、命名、结构、性能、错误处理、类型定义 |
| `B` | 当前无法/不宜优化，但仍存在改进空间（必须写清"为什么现在不能动"） |
| `C` | 死代码 / 未被引用的文件、导出、依赖、资源、样式、配置 |
| `D` | 潜在风险与隐患（安全、性能、兼容性、数据完整性、并发） |

## 2. 严重程度（每条发现必须标注）

| 级别 | 判定 |
| --- | --- |
| `P0` | 安全问题、数据损坏/丢失、可被远程触发 |
| `P1` | 确定性正确性缺陷、明显性能塌陷、资源泄漏、跨平台破坏 |
| `P2` | 可维护性问题：重复、耦合、复杂度、错误处理粗糙、类型过宽 |
| `P3` | 风格/一致性/可选改进 |

不要为了显得有产出而把 P3 写成 P1。**宁少而实，不多少而虚。**

## 3. 每条发现的格式

在 part 文件里用表格，一行一条，列固定：

```
| ID | 文件:行 | 问题描述 | 类 | 级 | 建议做法 |
```

补充说明（可选、且只在必要处）写在表格之后，用 `### 说明 · <ID>` 小节，给：
- 证据（实际命令与输出摘要、实测数字、grep 命中数）
- 为什么这算问题（不是"我觉得"，而是"会导致 X"）
- 建议的具体改法（能落到某个文件某段的粒度）

ID 规则：`<你的 scope 前缀>-<序号>`，例如 `WEB-001`、`CLI-007`、`PKG-013`、`DATA-002`。

## 4. 覆盖要求（防止抽样冒充全量）

1. 用 `git ls-files <你的范围>` 拿到**确定清单**，并把这个清单的数量写进 part 的"覆盖清单"章节。
2. 逐文件过一遍：源码读正文（大文件至少读全文并关注 1) 导出面 2) 错误处理 3) 重复 4) 长函数），配置/文档读结构。
3. 覆盖清单章节必须给出**完整文件列表 + 每个文件的结论**（`无问题` / `见 ID`），按目录分组。**不允许只列"抽查了 N 个"**。文件特别多的目录（例如 200+ 同构文件）可以按目录聚合，但必须写明聚合规则（例如"按 `*.test.ts` 逐条过，均无问题"）。
4. 若某文件确实无法读完（例如 1 万行以上的生成代码/证据 JSON），必须在覆盖清单里显式标注 `未逐行（原因）`，并说明替代手段（例如结构化抽样 + 生成来源核查）。**不许静默跳过。**

## 5. 死代码（C 类）的判定方法（必须给证据）

- 未引用导出：对 `packages/*/src/index.ts` 之外的导出符号，全仓 grep 引用点（`rg`/grep 工具）计数；0 外部引用且无同文件内使用 → 记 C。
- 未引用文件：`git ls-files` 里的文件，全仓 grep 其 basename（去扩展名）与 import 路径；0 命中且不是在 `bin`/入口/测试夹具/文档引用 → 记 C，并注明它的"应该被谁引用"。
- 未使用依赖：读每个 `package.json` 的 `dependencies`，全包 grep `from "<dep>"` / `require("<dep>")`；0 命中 → 记 C。
- 资源/样式：`apps/web/public/**`、`**/*.css` 里的文件与 class，grep 使用点。
- **注意**：`bin`、`main`、`exports` 入口，`*.test.ts`、`*.regressions.test.ts`、`benchmarks/**`、`scripts/**` 自身入口、`docs/**` 是被引用端，不要误判。`packages/*/src/index.ts` 的导出是包 API，被外部包消费也算被引用——要查全仓而不是查包内。

## 6. 风险（D 类）重点检查项

- 安全：子进程/fetch 的输入拼接、路径穿越（`resolve` 后是否校验前缀）、密钥落盘或进日志、`shell: true`、反序列化、权限/沙箱旁路（AGENTS.md 明令不得绕过 ToolOrchestrator / PermissionEngine / SandboxManager）。
- 并发：共享可变状态、`await` 之间的 TOCTOU、锁顺序、事件序列的稠密性假设。
- 兼容：Windows 路径/符号链接/编码（有大量 `EPERM symlink` 历史）、时区、大文件、`process.platform` 分支。
- 性能：同步 IO 在热路径、O(n²) 扫描、无上限的数组/Map 增长、每次请求重建大对象。
- 资源：未关闭的句柄/定时器/子进程、无超时的 await。

## 7. part 文件的章节结构（严格按此顺序）

```md
# <scope 名称> 审查结果
## 0. 结论摘要           ← 3-8 行：文件数、问题数按类/级分布、最值得先修的 3 条
## 1. 发现总表           ← 主表格，按级别降序
## 2. 分模块明细         ← 按目录分小节，每节先一句话定位，再表格
## 3. 覆盖清单           ← 完整文件列表 + 每文件结论
## 4. 存疑/需人工确认    ← 拿不准的，写清缺什么信息
```

## 8. 质量纪律

- **事实与推测分开**：实测数字、`file:line`、grep 命中数 = 事实；"可能导致"= 推测，必须标明。
- 不要复述代码做了什么；读者要的是"这里有什么问题、为什么、怎么改"。
- 同一模式在许多文件重复出现时，**合并成一条**，在说明里给出全部出现位置（用 grep 列表），不要写成 50 行。
- 不要提交、不要开 PR、不要碰 8787 服务。

## 9. 产出与回报

1. 写 part 文件到任务描述给你的路径。
2. 用 `send_message` 给 lead 发一条回报，内容 ≤ 40 行：part 路径、覆盖文件数/发现数（按类/级）、最该先修的 5 条（ID + 一句话）、以及你**主动放弃的部分**（若有，写清原因）。
3. 完成后把任务板上的任务标记 complete。
