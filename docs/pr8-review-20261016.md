## R1 · P1：从首个收到的事件推导基线，会把真实的前缀丢失当成正常日志

位置：`apps/web/src/deepseek/session.ts:116`，`sourceBaseline: visible[0]?.sequence ?? 0`。

这个调用方没有从 owner 的权威状态获取并验证基线，而是把待校验数据本身的
首序号作为正确答案；且它覆盖所有会话，不只 alias。因此普通会话漏掉0号事件、
或 alias 的 retired 日志没有读到时，剩余 `[1,2,...]` 都会被接受。投影函数的
默认0契约和单测仍然通过，真正的生产调用却绕过了该契约。

两个独立反例经真实 SessionService 的 `session/projections` 验证：普通会话
仅在 events.list 读取边界丢掉首事件；真实 owner 切换后仅让 retired owner
返回空前缀。精确 main 均报 not contiguous；候选均返回成功的投影。
这不是主张用户原始状态一定经过同一过程，而是证明 PR 会掩盖它本应发现的
真实缺失。`owners.ts:listEvents` 正常拼接 retired 与 live 的完整全局日志，
健康 alias 仍从0开始；两次真实模型切换后的控制流在 main 和 PR 都正常。

修正：保留完整日志的0基线校验，在 owner 层定位/拒绝缺失的 retired 前缀，
通过权威存储恢复用户历史；不要从收到的首事件、删目录或重编号推断完整性。
若未来明确支持截断日志，必须由经过独立校验的 owner 元数据声明基线，并将
“有意截断”与“丢失历史”区分，不把该选项自动应用到普通完整日志。

## R2 · P2：新接受的非零序列与 admissionBarrier 的数组索引混用

位置：`apps/web/src/deepseek/session.ts:108`，`events.slice(0, admissionBarrier)`。

admissionBarrier 是 `started.sequence`，而 slice 需要数组索引。以前 dense
0-based 时两者相等；PR 允许基线7以后，假设 pending turn 的事件序号为9，
实际位置却为2，slice(0,9) 就会包含本应等待 durable bindPromotion 的事件。

真实 actor + inbox 绑定屏障验证：平移0时正常；平移7时，绑定前 cursor 从0
推进到2，`user/message seq=2` 已发送但 source 没有 rpcId；绑定后同一条
`seq=2` 消息补上 `rpcId: review-pr8`。已发布记录因此发生变化，破坏 follow
流的不可变历史和队列请求相关性。此项针对 PR 新承诺接受的非零输入，不声称
当前 main 的健康0基线队列有同样问题。

修正：若保留经过独立证明的非零坐标，按序号确定屏障位置（或按序号过滤），
保证 started 及后续尚未绑定内容全部不可见；同时核查 sourceCursor、fork 与
sourceSequenceBySeq，新增非零基线下 bindPromotion 前后的一致性测试。
