## 1a. RESOLVED — the CI red was a test-side role assumption, not a product defect

**Diagnosis (hypothesis (a) from §1, confirmed).** `R7-F6-H` asserted
`platforms.ubuntu.status === "MEASURED_SAME_SHA"` while running with no `--os-label` override, i.e.
always as a **Windows** process. In that direction `ubuntu` is the *peer* slot and returns
`MEASURED_SAME_SHA`, so the suite was green locally. On a real ubuntu runner the roles are mirrored:
`platformSlot("ubuntu")` returns the early `MEASURED` (this process *is* ubuntu) and never reaches the
other-platform branch, so the same assertion failed. Reproduced by running the real script with
`process.platform` forced to `linux`:

| `--os-label` | `thisProcess` | `ubuntu` slot | `windows` slot | `crossPlatform` |
| --- | --- | --- | --- | --- |
| `windows-local` (what the suite used) | windows | `MEASURED_SAME_SHA` ← old assertion | `MEASURED` | `MEASURED_SAME_SHA` |
| `ubuntu-latest` (a real CI runner) | ubuntu | **`MEASURED`** ← old assertion demanded `MEASURED_SAME_SHA` → **FAIL** | `MEASURED_SAME_SHA` | `MEASURED_SAME_SHA` |

**The product is correct in both directions and was not changed.** §3 of
`docs/evidence/current-prereg-status.md` had already recorded the Linux-direction output.

**Fix (`349559d`), confined to the test file:** `R7-F6-H` now asserts the **peer role** (whichever
platform is not this process) instead of the hardcoded name `ubuntu`, and additionally pins that this
process's own slot is `MEASURED`; a new `R7-F6-H2` drives the `process.platform`→`linux` preload so the
mirrored direction is exercised locally on every run instead of first executing on CI.

**The forbidden shortcut was not taken:** the file was **not** re-added to the `vitest.config.ts`

## 7. Reproduction quick reference

```powershell
cd "D:\Harness Agent"
git rev-parse HEAD                        # 8fce634... (at the 2026-09-29 update)
git status --porcelain                    # MUST be empty before running any gate

node scripts/e4/r97-mutation-check.mjs    # anti-cheat gate: takes a lock, ~5-10 min, needs free memory

pnpm exec vitest run packages/evaluation/src/r97-mutation-check-guard.test.ts   # 51
pnpm exec vitest run packages/evaluation/src/r97-mutation-check.test.ts         # 32
pnpm exec vitest run --config apps/cli/test-infra/r0-gaps-vitest.config.ts      # 22
pnpm test:n0-gaps ; pnpm test:red-next-gaps ; pnpm typecheck ; pnpm docs:verify
```

**Memory note:** free memory dropped to ~1.1 GB with ~28 live git worktrees, and the gate was killed
mid-list three times (`exit=-1`), each time leaving a mutated file plus a stale lock. The gate needs
several GB free because it runs `tsc -b` plus vitest once per mutation.

**Recovery — do NOT use `git checkout -- .`.** That discards EVERY uncommitted change in the working
tree, including other teammates' in-flight work, and this repository has been worked by several agents
concurrently. It is the wrong tool even for a single-writer tree, because it cannot distinguish the
mutated file from anything else you had not committed yet.

Do this instead:

1. **Restore only the files the task owns**, by explicit path:
   ```powershell
   git status --porcelain                 # see which files are actually mutated
   git restore --source=HEAD --worktree -- <the exact paths the gate mutated>
   ```
   Never a bare `git checkout -- .`, never `git reset --hard`, never `git clean -fd`.
2. **Prefer an isolated worktree for the mutation gate.** It is the only way to be sure a killed gate
   cannot touch shared files at all:
   ```powershell
   git worktree add --detach "$env:TEMP\mutation-run" <sha>
   cd "$env:TEMP\mutation-run"; pnpm install --prefer-offline; pnpm build
   node scripts/e4/r97-mutation-check.mjs
   git -C "D:\Harness Agent" worktree remove --force "$env:TEMP\mutation-run"
   ```
   This also satisfies the gate's requirement that the tree be CLEAN, which a shared tree with
   concurrent writers almost never is.
3. Confirm the lock holder is actually dead before re-running; a stale lock plus a live PID is a
   different failure from a stale lock alone.

**Tree-cleanliness precondition (learned the hard way, 2026-09-29).** Several gates refuse to run on a
dirty tree (`CLEAN_TREE_REQUIRED`) — the `prereg` observer, the positive phases of
`prereg-production-e2e.mjs`, and the R5 formal chain. That refusal is correct, but it has a sharp
consequence: **a phase that never runs cannot fail, so defects reach CI green and only surface on the
clean CI runner.** That is exactly how a stale frozen fixture clock (`NOW = 1_700_000_000_000`,
2023-11-14) survived every local run and then failed both CI platforms with
`ARM_DEADLINE_EXCEEDED`. When you need a positive phase, build a clean worktree as in step 2 and run it
there — do not conclude "it passes locally" from a run that short-circuited on a dirty tree.
